PURPOSE

The controller reviews the non-production JSON-LD draft and the Prompt 02 QA report together and issues a formal decision. The controller is not Claude acting autonomously — the controller role is defined by this prompt and its decisions are constrained to the allowable outcomes below. No self-approval is permitted. No production authorization is issued from this prompt.

This prompt runs after Prompt 02 (Claude external QA one-zip) returns a PASS or WARN result.

If Prompt 02 returns FAIL, do not run Prompt 03. Resolve failures in Prompt 01 first, then re-run Prompt 02.

OPERATOR INSTRUCTION

Paste this prompt after Prompt 02 returns a PASS or WARN result. Provide the draft, evidence table, held fields table, and Prompt 02 QA report in the input. The controller will return one of the defined decisions.

---

ALLOWABLE CONTROLLER DECISIONS

The controller must issue exactly one of the following decisions:

ACCEPT
  Condition: Draft passes all checks. QA is PASS or WARN with no blocking issues. No held fields. No blocked modules. No invented content.
  Next step: Proceed to Prompt 04 (validator results review).

MODIFY
  Condition: Draft has non-blocking issues (e.g., a WARN from QA) that require a targeted correction but do not require full regeneration.
  Next step: Specify exact modifications required. Operator or Claude applies modifications. Controller confirms modified draft before proceeding to Prompt 04.
  Note: Modified draft must be re-reviewed within this prompt before ACCEPT is issued.

REJECT
  Condition: Draft has a blocking defect — e.g., a QA FAIL, a held field was emitted, a blocked module is present, or an invented field was found.
  Next step: Draft is discarded. Operator must return to Prompt 01 and regenerate with the defects corrected.

DEFER
  Condition: The run cannot proceed due to an external condition — e.g., evidence map incomplete, fingerprint mismatch discovered, owner approval required for a field.
  Next step: Suspend the run. Document the blocking condition. Resume only when the condition is resolved.

HUMAN_REVIEW_REQUIRED
  Condition: The controller has identified an ambiguity or edge case that requires package owner judgment before the run can continue.
  Next step: Escalate to the package owner. Do not proceed until the owner resolves the ambiguity and explicitly authorizes continuation.

---

MODIFICATION RULES (if MODIFY is issued)

If the controller issues MODIFY:
- State exactly which field(s) or node(s) require modification
- State the reason for the modification
- State the corrected value(s) with Phase 0 or evidence source
- Do not modify held fields — if a held field issue was found, issue REJECT instead
- Do not add blocked modules — if a blocked module was found, issue REJECT instead
- After modification is applied, return the modified draft here for confirmation before issuing ACCEPT

---

REGENERATION RULES (if REJECT is issued)

If the controller issues REJECT:
- State exactly which defect caused the rejection
- State the applicable stop code (e.g., STOP_HELD_FIELD_VIOLATION, STOP_BLOCKED_MODULE_ATTEMPTED, STOP_CONTENT_INVENTED)
- The operator must return to Prompt 01 and rebuild the draft
- The rebuilt draft must go through Prompt 02 and Prompt 03 again before proceeding

NON-AUTHORIZATION STATEMENT

The controller does not self-approve the draft for production. An ACCEPT decision from Prompt 03 means the draft is suitable to proceed to Prompt 04 (validator results review). It does not mean the draft is approved for implementation. Validator review (Prompt 04), independent analyzer review (Prompt 13), controller post-analyzer review (Prompt 14), and explicit human approval are all still required before any implementation handoff.
